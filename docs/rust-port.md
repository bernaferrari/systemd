# Rust Port Syncing

This document captures the practical workflow for an upstream-tracking Rust shadow port.

## Repository navigation

- `docs/rust-port-workspace.md` defines the only supported crate placement and
  internal dependency direction.
- `docs/rust-rm-rf-shadow-plan.md` records the staged safety and parity gates
  for the currently unselected shared `rm_rf` prototype.
- `tools/rust-port/README.md` indexes synchronization, ABI, architecture,
  safety, and reporting tools without moving their stable CI entry points.
- `tools/rust-port/RUST_FIXTURE_CATALOG.md` explains how to query Rust-linked
  `tests-extra` fixtures and requires semantic names for new comparisons.
- `src/<subsystem>/rust/` remains beside its upstream C subsystem. Focused
  Rust-only decomposition belongs below that directory; parallel top-level or
  nested Cargo workspaces are forbidden.

## Invariants

- `c_file` (or `c_paths`) points at upstream C sources and is the canonical drift input.
- `rust_file` (or `rust_paths`) points at the Rust twin paths in the same
  upstream tree.
- Status and mapping fields are declared in `tools/rust-port/map.toml`; that file is the source of metadata.
- `last_synced_upstream_blob` and `last_synced_rust_blob`, or their
  path-keyed plural forms, are explicit review markers and are never
  auto-generated by scripts.
- Meson remains the build authority; these tools only help with synchronization hygiene.

## Meson Flags

Only the following Rust options currently exist:

- `-Drust=enabled` builds the `src/basic/rust` shadow static library used by
  `tests-extra`.
- `-Drust-core-pid1=enabled` additionally builds the experimental incomplete
  Rust PID1 as a non-installed developer artifact. It requires
  `-Drust=enabled`, is permitted only with `-Dmode=developer`, and never
  replaces the installed C `systemd`.
- `-Drust-init-milestones=enabled` enables experimental Rust init milestone
  tests.

There are no `rust-basic`, `rust-shared`, `rust-libsystemd`, `rust-core`, or
`rust-shadow-tests` Meson options. Most Cargo workspace crates are not Meson
artifacts and must not be counted as shipped replacements.

Every workspace package is also marked `publish = false`, enforced by the
workspace architecture gate. These internal shadow crates are not crates.io
release artifacts; publication requires a future, explicit package-by-package
review after the relevant runtime is integrated and validated.

Cargo CI is therefore check/lint-only at workspace scope. Crates such as
`systemd-basic-rs` call back into C and cannot truthfully be tested by
`cargo test --workspace`; linked comparison coverage must come from a
`-Drust=enabled` Meson build. CI compiles and runs only the reviewed shadow
targets whose explicit ABI surfaces are currently closed. The remaining
registered targets stay visible as ratcheted link debt rather than being
presented as passing coverage.

## C and `libc` Boundary Policy

The port is not trying to be “C-free” at the Linux ABI boundary. Use the
`libc` crate narrowly for kernel/libc constants, layouts, syscalls that have no
faithful safe wrapper, errno values, and allocations whose ownership crosses a
C ABI. Do not pass `Vec`, `String`, `Box`, or Rust-global-allocator memory to C
code that will release it.

Keep those operations in small reviewed boundary modules:

- expose safe Rust types and `Result`-based ownership internally;
- validate lengths, aliases, alignment, and nullability before raw operations;
- use `libc::malloc/free` only where C owns or releases the allocation;
- prefer a mature safe Rust/standard-library wrapper when it preserves exact
  systemd/Linux semantics;
- do not grow ad-hoc callbacks into the old C implementation as a substitute
  for porting architecture.

The target is a Rust-owned design with a thin auditable Linux/C ABI shell, not
either pervasive C coupling or a portability abstraction that hides required
Linux behavior.

## Status Model

Canonical values used in CI policy:
- `shadow`: C and Rust are both available and compared in tests.
- `replace`: Rust is the production implementation.
- `fallback`: Build can switch back to C immediately.

Legacy values kept for existing entries:
- `todo`, `in-progress`, `done`

Recommended migration:
- keep legacy values for old rows as-is
- for new rows use one of `shadow`, `replace`, or `fallback`

## Map File Schema

`tools/rust-port/map.toml` is a TOML table per module. Machine-readable keys for tooling:

- exactly one of `c_file` or `c_paths` for the upstream C authority
- exactly one of `rust_file` or `rust_paths` for the Rust twin
- optional `scope` plus `rust_scope_paths` for an idiomatic Rust subsystem
  inventory; a scope path may be a Rust file or a directory recursively
  containing `*.rs`
- optional `rust_interface_paths` for ABI headers and other owned interfaces;
  scoped `rust_paths` must exactly equal the source inventory plus these
  interfaces
- optional `contract_file` below `tools/rust-port/contracts/<subsystem>/`
- scoped entries with `c_paths` must declare `c_provenance_edges`, one inline
  table for every mapped C path. A `kind = "direct"` edge names exact
  `rust_paths`; a `kind = "transitive"` edge names direct C paths in `via`
  and has a non-empty review `rationale`.
- `status`
- `tier`
- `tests`
- `symbols`
- `owner`
- `last_synced_upstream_blob`
- `last_synced_rust_blob`
- `last_synced_upstream_blobs` and `last_synced_rust_blobs` when the
  corresponding side has multiple paths; these must be exact path-to-blob
  tables with neither missing nor extra paths
- `last_reviewed_upstream_blob(s)` and `last_reviewed_rust_blob(s)` for a
  reviewed but incomplete snapshot that must detect future drift without
  asserting parity
- `notes`

### Source structure versus behavioral fidelity

Directories are inventory boundaries, never semantic authority. Every C
source, header, generated table, or other input that owns behavior remains an
explicit path in `c_paths`, with its own review hash. A Rust scope may freely
split that behavior into safe cores, parsers, ABI adapters, and platform
modules, but every recursive Rust leaf must be materialized in `rust_paths`.
Adding a child module therefore forces a map review instead of silently
escaping synchronization.

Scoped Rust leaves use a preamble marker such as:

```rust
// PORT-SYNC: scope=basic.devnum-util; authority=src/basic/devnum-util.c,src/basic/devnum-util.h
```

Each scoped entry also owns a semantic contract. Contracts describe observable
surfaces rather than source layout: C/Rust symbols, ABI, byte treatment, errno
behavior, ownership, success/error output publication, environmental
dependencies, known exclusions, deliberate deviations, and whether evidence
is static-only or runtime-verified. Rust-specific internal behavior is welcome
when it is unobservable at the contract boundary. Observable deviations must
be explicit and cannot contribute to a parity claim.

`last_reviewed_*` means “this partial contract was compared at these exact
blobs.” `last_synced_*` means completed parity. A reviewed snapshot is useful
provenance, but never satisfies `sync_status = "synced"`.

Paths must be repository-relative, normalized, and exist. `stale-check.py`
compares every recorded `last_synced_*` hash against `git hash-object` for the
corresponding path. A missing anchor is not a successful comparison:
non-strict mode reports it as unanchored, while strict mode rejects every
sticky `done`, `shadow`, `replace`, or `fallback` claim without a complete
reviewed anchor set.

Every mapped Rust source must also make its ownership visible in its first
16 lines:

- `// PORT-SYNC: ...` means the map supplies one or more current C authority
  paths for this Rust source. Scoped entries must include the exact
  `scope=<name>` owner.
- `// PORT-GAP: ...` means the row intentionally has no current C authority,
  remains `todo`/`in-progress`, and explains why ownership must be re-audited.

The annotation is a navigation aid, not proof of parity. The exact path set is
owned by the map. Likewise, `sync_status = "synced"` is permitted only when
both sides have complete reviewed blob anchors. An unanchored row may be
truthfully `needs_review` or `partial`; “zero stale anchored rows” must never
be presented as “all unanchored rows are current.”

### Direct and transitive C provenance

For a scoped Rust port, the `PORT-SYNC` authority list is deliberately its
direct authority only. The manifest's `c_provenance_edges` makes the complete
`c_paths` closure machine-checkable: every C path has exactly one edge; direct
edges list every Rust leaf whose preamble declares that source; transitive
edges route through one or more direct paths and explain why the dependency
remains in scope. The metadata gate rejects missing or duplicate edges,
unmapped Rust leaves, unexplained closure paths, and markers that present a
transitive dependency as direct authority. Directories remain Rust inventory
boundaries, never C authority.

The `src/fundamental/*-fundamental.{c,h}` spelling was renamed upstream in
`74d392ed1b` to canonical filenames such as `bootspec.c`, `sha256.h`, and
`string-util.c`. `map.toml` and `PORT-SYNC` comments must record only those
current paths. The sync metadata gate keeps the reviewed rename table so a
retired spelling is reported with its canonical replacement instead of being
mistaken for an ordinary missing source file.

## Parity Review Checklist

Copy this checklist into the review description whenever a port is added,
expanded, or re-synchronized:

- [ ] Identify every C source/header/table that owns the behavior and record
  the exact many-to-many `c_paths`/`rust_paths`.
- [ ] For decomposed Rust, declare one subsystem `scope`, inventory every
  recursive Rust leaf, and give shared implementation files one owner plus
  explicit dependencies rather than multiple owners.
- [ ] Describe each reviewed behavioral surface in a contract, including
  explicit exclusions and static-only versus executed evidence.
- [ ] Add a preamble `PORT-SYNC` marker, or a documented `PORT-GAP` while the
  row remains incomplete.
- [ ] Compare native types, constants, errno/return values, NULL/empty inputs,
  borrowed versus allocated outputs, mutation ordering, and failure
  publication.
- [ ] Establish current-C signature/table/static authority and differential
  tests appropriate to the surface. Do not count a header or forward
  declaration as an implementation.
- [ ] Keep filesystem, allocator-fault, kernel, cross-target, and runtime
  evidence explicitly separate from static evidence; file named follow-up
  work when those checks cannot run.
- [ ] Set `shadow`/`replace`/`fallback`, or `sync_status = "synced"`, only after
  the reviewed C and Rust path hashes are recorded. Never stamp hashes merely
  to make a gate green.
- [ ] Run the sync metadata, strict stale, changed-file report, subsystem
  authority, formatting, and diff checks; record any unrelated aggregate
  failures without weakening the focused gate.

## Updating After an Upstream C Change

1. Run `diff-report.py` over the upstream range. Each `upstream:` line names a
   mapped C authority requiring review; a `rust:` line only says that a twin
   changed, not that parity was preserved.
2. Read the current C implementation and all mapped authority files. Decide
   whether the Rust design still maps cleanly. If the C ownership moved,
   update the exact path arrays before changing code.
3. Re-port the behavior into a safe core with narrow ABI/runtime boundaries.
   Prefer a focused rewrite when the C invariants changed materially; avoid
   layering compatibility conditionals over a no-longer-comparable design.
4. Update differential/static authority coverage and run the parity checklist.
   If evidence is incomplete, leave the row `in-progress` with
   `sync_status = "needs_review"` or `"partial"`.
5. After a partial static review succeeds, record exact `last_reviewed_*`
   snapshots and keep `sync_status = "partial"`. Only after the declared
   behavior is complete and the required runtime/cross-target evidence exists
   may those be promoted to `last_synced_*` with `sync_status = "synced"`.
   Run strict stale and behavior-contract checking after either update.

## CI Checks

1. Reject sticky claims without anchors, missing paths, and drift in every
   anchored path:

```sh
python3 tools/rust-port/stale-check.py --strict --require-existing-paths \
    --map tools/rust-port/map.toml
```

2. Enforce preamble ownership markers and reject unanchored
   `sync_status = "synced"` labels:

```sh
python3 tools/rust-port/sync-metadata-gate.py
```

When comparing a port branch to the official source tree, also verify every
mapped C authority directly from that tree without checking it out:

```sh
python3 tools/rust-port/sync-metadata-gate.py --upstream-ref origin/main
```

3. Validate semantic contracts separately from source-layout synchronization:

```sh
python3 tools/rust-port/test-behavior-contract.py
python3 tools/rust-port/check-behavior-contract.py
```

4. Show touched modules before review:

```sh
python3 tools/rust-port/diff-report.py --worktree --map tools/rust-port/map.toml
```

5. Show touched modules in a commit range:

```sh
python3 tools/rust-port/diff-report.py --range HEAD~1..HEAD --map tools/rust-port/map.toml
```

6. Exercise the many-to-many stale and reporting workflow fixtures:

```sh
python3 tools/rust-port/test-stale-check.py
python3 tools/rust-port/test-sync-workflow.py
```

7. Reject completed port-map claims backed by missing declared source anchors,
   source metadata, or notes that still document fail-closed/incomplete
   behavior. This also verifies that the incomplete Rust PID1 remains blocked
   in Meson release mode and visibly warned in developer mode:

```sh
python3 tools/rust-port/truthfulness-gate.py
```

8. Keep incomplete Rust code out of the installed production graph. The core
   gate pins the current C implementations for unported PID1 behavior, the
   basic gate keeps its Rust archive shadow-test-only, and the general
   selection gate rejects an unreviewed Cargo/Meson production path:

```sh
python3 tools/rust-port/check-core-c-retention.py
python3 tools/rust-port/check-basic-shadow-boundary.py
python3 tools/rust-port/check-rust-production-selection.py
```

8. Ratchet every Rust-side C header declaration against an explicit exported
   `extern "C"` Rust symbol. The checked-in baseline records historical
   unbacked declarations so they may decrease but never silently increase.
   Independently ratchet manual `rs_*` prototypes in C sources of Meson
   executables that link `libsystemd_basic_rs.a`; those declarations bypass
   Rust-owned headers and remain artifact-specific link debt, not evidence that
   the target works:

```sh
python3 tools/rust-port/rust-ffi-inventory-gate.py
python3 tools/rust-port/check-c-char-abi.py
python3 tools/rust-port/check-registered-test-rust-ffi.py
```

   The C-character gate rejects literal Rust `i8` in extern-C function
   definitions, declarations, and function-pointer types, and raw
   `*const i8`/`*mut i8` spellings throughout `src`. C `char` signedness is
   target-defined, so ABI surfaces must retain `libc::c_char` symbolically;
   byte-oriented implementation code should use `u8`. Reviewed `repr(C)`
   layouts remain the responsibility of their subsystem-specific ABI gates.

7. Validate the single-workspace, single-lockfile, unique-target, and module-size architecture:

```sh
python3 tools/rust-port/workspace-architecture-gate.py
```

   Classify every `src/core/rust/lib.rs` module against the authoritative
   Meson-selected `systemd` Cargo binary:

```sh
python3 tools/rust-port/core-runtime-reachability-gate.py
```

   The checked-in baseline records the complete PID1 binary source tree and
   requires every declared library module to be explicitly recorded as either
   `runtime-reachable` or `compiled-but-disconnected`. New, removed, moved, or
   reclassified module debt requires deliberate `--write-baseline`
   regeneration and review. This is a conservative lexical Rust import graph
   only: neither compilation nor `runtime-reachable` claims behavioral parity,
   PID1 completeness, or production readiness.

   The parser follows crate-root-correct binary and library submodules, direct
   and grouped `crate::`/`systemd_core_rs::` paths, grouped simple crate aliases,
   and direct crate-root reexports. It masks comments and Rust string, raw
   string, byte-string, character, and byte-character literals, and skips
   standard `#[cfg(test)]` modules. It fails closed on `#[path]`, `include!`,
   relevant unsupported `cfg` imports/modules, module declarations in macro
   bodies, nested inline external modules, and glob or nested crate-root
   reexports. Dynamic dispatch and general macro expansion remain outside this
   lexical classification and must not be used to hide PID1 module wiring.

## Expected Commit Flow

- Update `tools/rust-port/map.toml` entries when behavior parity and tests are accepted.
- Keep C implementation in place until Rust path passes CI for the intended scope.
- Use commit notes to mention blob IDs updated and tests run.
- Maintain migration ordering in `docs/rust-port-plan.md`.
